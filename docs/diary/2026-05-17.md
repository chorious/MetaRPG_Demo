# 2026-05-17 日记

今天的项目推进有点像从一堆互相纠缠的线里，慢慢把主线拎出来。

一开始还在想一些很具体的外部工具问题，比如博德之门 3 的 Nexus Mods 更新检测。后来意识到，其实下载记录里按 update 排序就能解决大部分需求。这件事挺典型：有些问题看起来需要写系统，实际只需要找到已有平台的正确入口。

随后看了一下博德 3 有没有拓展内容类 mod，也顺带把注意力带回了 MetaRPG。真正的大头还是 `E:\GameDesign\MetaRPG_Dev` 这个项目本身：它和原先规划之间的差距已经开始变得明显。`reviewVer0.5.2.md` 里确认了一件事：UPF bridge 有意义，但不是眼下最该继续扩张的方向。桥接可以通向 playable shell，但如果 Python 叙事核心本身还是 raw 的，桥接只会把粗糙体验搬到另一个壳里。

今天最重要的判断，是对“玩家行为是否能被抽象穷尽”的怀疑。这个怀疑其实非常关键。早期实现里，code 试图把玩家动作拆成越来越多的类别、规则、检查项，但越做越像玩家在面对系统，而不是面对故事。真正的核心应该是：LLM 写故事，code 负责整理局部上下文和做事实检查。也就是说，code 不该喧宾夺主，它应该成为叙事的边界和证据系统。

这个判断后来被进一步整理成四层结构：

```text
1. 世界状态
2. 作家 LLM
3. 审核 LLM
4. 编辑 LLM
```

再加上硬 Auditor，也就是 Translator：把自然语言翻译成结构化 claim，再跑结构性对齐率。这样一来，项目的重点就不再是“写更多规则穷尽玩家行为”，而是“让 Writer 生成大胆、生动的文本，再让 Auditor 和 Editor 把它校准回世界”。

今天还讨论了 Teacher。Teacher 不应该热更新底层代码，也不应该每轮自动改规则库。更合理的位置是规则策展人：每一轮收集其他 Agent 认为值得上升的经验，如果确实稳定、反复、有价值，再交给 Teacher 校对成候选规则。这样既保留学习能力，又不让系统底层在运行中失控。

`MetaRPG_Agent_ver0.6_plan.md` 和故事 prompt 参考也在这个方向上形成了：先不管 UPF，把 Python agentic loop 跑通。Greyfen 酒馆场景成了一个很好的小型验证场：玩家点酒、喝酒、追问消息、观察玛拉反应。这个场景小，但足够暴露问题：LLM 是否能写出故事感，Translator 是否能抽取 claim，Hard Auditor 是否过宽或过窄，Soft Auditor 是否能抓住“像任务播报而不像故事”的粗糙感。

今天也看到了第一个明显的结构性风险：层越来越多，项目越来越慢，文件越来越碎。Writer、Translator、Hard Auditor、Soft Auditor、Editor、Teacher、Committer、Scorecard、Run Logger，每个东西都有意义，但如果没有统一 runner 和统一 artifact 标准，项目会很快变成一堆局部正确但整体难调的模块。

所以今天最后沉淀下来的方向是：

```text
主线：v0.6 agentic Python pipeline
暂停：UPF bridge
基线：v0.1-v0.5 deterministic legacy engine
验证目标：Greyfen 5-turn beer loop
工程重点：runner / logger / scorecard / prompt contract
```

对我来说，今天最大的收获不是某个文件写完了，而是项目的评价标准变清楚了。之前的问题经常像是在问“能不能模拟一切玩家行为”。现在的问题更具体：

```text
StoryPacket 有没有给 Writer 足够的局部故事？
Writer 有没有写出像故事的文本？
Translator 有没有把文本里的事实 claim 抽出来？
Hard Auditor 有没有守住世界边界？
Soft Auditor 有没有指出体验粗糙的地方？
Editor 有没有把问题切成局部 rewrite？
Committer 有没有只提交被允许的后果？
Scorecard 有没有诚实地反映体验？
日志有没有留下足够证据？
```

这组问题比“抽象穷尽玩家行为”要更健康。

今天的结论：MetaRPG 不该继续堆规则模拟玩家，而应该把 LLM 当成故事发动机，把 code 当成叙事证据和世界边界。接下来最重要的不是再加 Agent，而是让现有 Agent 的输入输出、日志和评估变得可靠。
